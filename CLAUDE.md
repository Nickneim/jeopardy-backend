# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Spring Boot 4 / Java 21 backend for a multiplayer Jeopardy game. Game content (games, categories, clues, daily doubles) lives in PostgreSQL. Live game sessions are held in memory and played over STOMP WebSockets.

The React frontend lives in a separate repository. **`docs/api.md` is the contract between them** (REST and STOMP endpoints, payloads, `GameSessionResponse` fields by state, rules, timings, error codes, TypeScript types, known limitations). Any change to an endpoint, payload, field, state, timing or error code must update it in the same commit. The pre-commit hook in `.githooks/` enforces this: it rejects a commit that stages DTOs, controllers, `ApiExceptionHandler`, `GameErrorCode`, `GameSessionState` or `GameSessionTimeouts` without `docs/api.md`. Enable it once per clone with `git config core.hooksPath .githooks`; for a change that really doesn't touch the contract, commit with `SKIP_API_DOCS_CHECK=1`.

## Commands

**To run tests, use `scripts/test.sh`** (bash). It loads `.env`, runs Gradle quietly and prints only the totals, each failing test with its message and location, or the compiler errors; the full output goes to `build/test-output.log`. Extra arguments go to Gradle, and `TASK=build` runs the build instead of `test`:

```bash
scripts/test.sh                                    # all tests
scripts/test.sh --tests "*GameSessionTest*"        # a class or pattern
TASK=build scripts/test.sh                         # compile + all tests
```

Otherwise use the Gradle wrapper (`./gradlew` in bash, `.\gradlew.bat` in PowerShell). It doesn't load `.env`, so most tests fail to connect without the variables exported.

```bash
./gradlew build                     # compile + run all tests
./gradlew bootRun                   # run the app
./gradlew test                      # all tests
./gradlew test --tests "com.nickneim.jeopardy.session.model.GameSessionTest"
./gradlew test --tests "*GameSessionTest.chooseClue*"   # single method / pattern
```

There is no linter or formatter configured.

### Environment / database

- The app reads `DATABASE_URL`, `DATABASE_USERNAME` and `DATABASE_PASSWORD` (`application.yaml`). Locally they come from the git-ignored `.env`, which the IntelliJ run config `.run/JeopardyApplication.run.xml` loads. `bootRun` does **not** load `.env` on its own.
- Tests annotated `@ActiveProfiles("test")` use `TEST_DATABASE_URL`, `TEST_DATABASE_USERNAME` and `TEST_DATABASE_PASSWORD` (`src/test/resources/application-test.yml`). They need a real, reachable Postgres. There is no H2 or Testcontainers.
- `JeopardyApplicationTests` has no test profile, so it needs the main `DATABASE_*` variables.
- **Error details:** `spring-boot-devtools` (`developmentOnly`, so active in the IDE and `bootRun`) turns on `spring.web.error.include-stacktrace`, `include-message` and `include-binding-errors`, which sent stack traces to clients. `application.yaml` sets all three to `never` explicitly, which wins over devtools; the `dev` profile (`application-dev.yaml`, `SPRING_PROFILES_ACTIVE=dev`) turns them back on for local debugging. `ErrorResponseIntegrationTest` adds devtools' defaults the way devtools does and checks nothing leaks.
- **Browser origins (CORS):** the frontend runs on another origin (Vite dev server, `http://localhost:5173`), so browsers check it on every REST call and the `/ws` handshake. Allowed origins come from `app.cors.allowed-origins` (`CorsProperties`), overridable with the comma-separated `ALLOWED_ORIGINS` environment variable. `WebCorsConfig` applies them to `/api/**` and `WebSocketConfig` to `/ws`. Test clients send no `Origin` header, so only `WebCorsConfigTest` and the WebSocket origin tests exercise this.
- Hibernate runs with `ddl-auto: validate`. All schema changes go through Flyway migrations in `src/main/resources/db/migration/` (`V<n>__description.sql`), and the JPA entities must match them exactly. `clue.type` is a Postgres enum, mapped with `@JdbcType(PostgreSQLEnumJdbcType.class)`.

## Architecture

There are two top-level feature packages under `com.nickneim.jeopardy`. Each has its own `controller` / `dto` / `service` / `exception` subpackages.

### `game`: persistent content (REST, read-only)

- `Game` → `Category` → `Clue` JPA entities. `GameDailyDouble` is a join entity with a composite key (`GameDailyDoubleId`).
- **The round is derived from `Category.columnNumber`, not stored:** columns 1–6 are Jeopardy, 7–12 are Double Jeopardy, and 13 is Final Jeopardy (`GameRound.fromColumn`). Clue value is also computed (`Clue.getValue()`): `200*row` in J! ($200–$1000), `400*row` in DJ! ($400–$2000), and a flat 2000 in Final.
- Endpoints: `GET /api/games` (paged, optional `season`, `title`, `from`, `to` and `playable` filters, combined in `GameFilter` and turned into a JPA `Specification` by `GameSpecifications`; `playable` is an `EXISTS` subquery, and each summary's `clueCount` comes from one grouped query for the page's ids, `GameService.countClues`, so listing never loads clues). Some imported games have no clues; they're valid content, but creating a session from one returns 422 (`UnplayableGameException`), `GET /api/games/{id}`, `GET /api/games/seasons` and `GET /api/clues/{id}`. Seasons are strings and not all numeric (specials like `"jm"`): `GameService` sorts numbered seasons numerically, highest first, then the specials by their latest game. DTOs are records with static `from(entity)` factories. `GameResponse` splits categories into `jeopardyRound`, `doubleJeopardyRound` and `finalJeopardy`.
- REST errors are mapped to `ApiErrorResponse` in `exception/ApiExceptionHandler`.

### `session`: live gameplay (in memory, WebSocket)

- `GET /api/game-sessions` lists sessions for a lobby (paged in memory by `GameSessionService.listSessions`, newest `createdAt` first, `FINISHED_GAME` only with `includeFinished`; `GameSessionSummaryResponse`, which must never hold tokens). `POST /api/game-sessions` with `{gameId}` creates a session and returns its UUID. `GET /api/game-sessions/{id}` returns the current `GameSessionResponse` (for clients catching up). `POST /api/game-sessions/{id}/players` with `{playerName}` joins it and returns `{playerId, token}` to the joining player only. The rest of the game runs over STOMP. `createdAt` comes from the `Clock` bean (`ClockConfig`), so tests can control it; `GameBoard` carries the game's id and title for the list (null for boards not from the database).
- **Player identity comes from the connection, never from a message.** Each player has a secret token (`PlayerTokens`, 256-bit random). The client sends it as the `player-token` header on STOMP CONNECT; `PlayerAuthenticationInterceptor` looks it up in `PlayerTokenRegistry` and attaches a `PlayerPrincipal(sessionId, playerId)` to the connection. No token means an anonymous connection (it can subscribe and watch, but actions get `UNAUTHENTICATED`); an unknown token rejects the connection. `GameSessionWebSocketController.playerId(...)` resolves the acting player and rejects a token from another session (`PLAYER_NOT_IN_SESSION`). Reconnecting with the same token restores the identity. **Tokens must never be broadcast or logged**: `PlayerResponse` excludes them and `GameSessionResponseTest` checks the JSON. The interceptor depends on `PlayerTokenRegistry`, not `GameSessionService`, to avoid a circular dependency through the broadcaster's messaging template. It rejects an unknown token by sending a STOMP ERROR frame to the (lazily injected) `clientOutboundChannel`, which makes Spring close the connection, and dropping the CONNECT. **Don't throw from inbound interceptors:** with `setPreserveReceiveOrder(true)`, Spring's `OrderedMessageChannelDecorator` catches and only logs their exceptions, so the client would get no ERROR frame and hang.
- **Sessions play from a `GameBoard`, never from JPA entities.** `session.board` holds immutable records (`GameBoard` → `BoardRound` → `BoardCategory` → `BoardClue`); each `BoardClue` stores its own row (1-based, gaps allowed, unique per category), value, Daily Double flag, clue type and media URL (a URL exactly when the type isn't `TEXT`, as in the database); each `BoardCategory` keeps its comments. Game progress is not on the board: `GameSession` keeps the set of played clue ids for the whole game, and the available clues are derived (`board.getClueIds(round)` minus played). `GameBoard.from(game)` copies a database `Game` into a board, following the `from(entity)` factory convention. It reads lazy collections, so it must run inside a transaction: `GameBoardService.loadBoard(gameId)` wraps it in a read-only one. These two are the only session code that touches entities. Custom games can build a `GameBoard` directly. Rounds are played in `GameRound` order and rounds without clues are skipped.
- STOMP setup (`config/WebSocketConfig`): the endpoint is `/ws`, client sends go to `/app/...`, and the simple broker serves `/topic` and `/queue`. `setPreserveReceiveOrder(true)` keeps each connection's messages in order; without it the inbound thread pool can reorder them (a client's second Final Jeopardy wager was overwritten by its first).
  - Client → server: `/app/sessions/{id}/start | update-timers | update-settings | kick | leave | choose-clue | buzz | answer | place-daily-double-wager | place-final-jeopardy-wager | answer-final-jeopardy` (`GameSessionWebSocketController`). Request bodies never contain the acting player's id (`kick`'s `playerId` is the target); `start`, `buzz` and `leave` take no body.
  - Server → clients: after every state change, the full `GameSessionResponse` is broadcast to `/topic/sessions/{id}` (`GameSessionBroadcaster`). It includes `board`: the current round as a rectangular grid of categories × rows, where each `ClueSlotResponse` has a clue id, value and `ClueSlotStatus` (`AVAILABLE`, `PLAYED`, `EMPTY`). Everyone receives it, so it must never contain questions, answers or Daily Double flags (`GameSessionResponseTest` checks the serialized JSON). The clue in play is sent separately as `currentClue` (`CurrentClueResponse`, null when no clue is in play): a Daily Double hides its question, `clueType` and `mediaUrl` until the wager is placed, and the answer is only included in `REVEALING_ANSWER`. Turn and buzzer info is sent as `playerChoosingClue`, `playerAnswering` and `playersLockedOut`, and a placed Daily Double wager as `currentClue.wager`. `clueAnswers` lists every answer to the current clue (submitted text, null on timeout, and whether it was correct, never the stored answer); `GameSession.clueAnswers` is cleared when a clue is chosen and when Final Jeopardy starts. These come from `GameSession` getters that only return a value while it is meaningful, because the underlying fields (`playerWhoBuzzed`, `playersAlreadyBuzzed`, a player's `wager`) are not cleared between clues. Don't expose those fields directly.
  - Errors: `InvalidGameActionException`, `GameSessionNotFoundException` and invalid payloads (`INVALID_REQUEST`) go only to the sender, at `/user/queue/errors`, as `GameSessionErrorResponse(code, message)` with a `GameErrorCode`.
- **`GameSession` (model) is a plain, non-Spring state machine** that holds all the game rules. Its states are in `GameSessionState`: `WAITING_FOR_START → CHOOSING_CLUE → [WAITING_FOR_DAILY_DOUBLE_WAGER] → REVEALING_CLUE → WAITING_FOR_BUZZER ⇄ WAITING_FOR_ANSWER → REVEALING_ANSWER → CHOOSING_CLUE …`. Once every clue in a round is used, it moves to the next round (`enterRound`). Entering the Final Jeopardy round starts Final Jeopardy instead of `CHOOSING_CLUE`; a board without one goes to `FINISHED_GAME`. Illegal actions throw `InvalidGameActionException`. On a daily double, the buzzer is skipped and the chooser answers using their wager; the maximum wager is the higher of their score and the highest clue value in the current round (`GameBoard.getHighestValue`).
- **Final Jeopardy** (one clue per board, enforced by `GameBoard`): `FINAL_JEOPARDY_WAGERING` (category shown; every player wagers 0 up to their score, so a score of 0 or less can only wager 0) → `FINAL_JEOPARDY_ANSWERING` (clue shown; every player answers) → `FINAL_JEOPARDY_REVEALING` (correct response, wagers and answers shown) → `finishFinalJeopardyReveal` applies every wager (no answer counts as wrong) → `FINISHED_GAME`. Each phase ends only on its timer. Players can change their wager or answer until then, a missing wager counts as 0, and scores only change after the reveal. The broadcast's `finalJeopardy` (`FinalJeopardyResponse`) shows per player only whether they've wagered/answered until the reveal; `FinalJeopardyResponseTest` checks the JSON.
- **Host and leaving** (all in `GameSession`): the first player to join is the host (`hostPlayerId`), always the lowest active id; only the host can `startGame`, `updateTimeouts` and `kick` (`NOT_HOST`). `leave`/`kick` mark the player `leaving`; `removeDepartedPlayers` then removes every leaving player who holds no role (`holdsRole`: `playerChoosingClue` or `playerAnswering`, only in the clue-round states), so a departed chooser keeps control until someone answers correctly and a departed buzzer stays until their answer times out. Call `removeDepartedPlayers` after any transition that can end a role. Removal erases the player everywhere (players, buzz locks, `clueAnswers`, Final Jeopardy maps): every player id in a response must belong to someone in `players`. Leaving players can't act (`requireActivePlayer`), and "everyone has buzzed" counts only active players. Ids come from a counter and are never reused, because a stale connection's `PlayerPrincipal` would otherwise act as the new player. The service revokes the departed player's token and closes their connections through `PlayerConnections` (an ERROR frame per STOMP session; `PlayerAuthenticationInterceptor` records connections on CONNECT and forgets them on DISCONNECT), so a reconnect is rejected like any unknown token. A dropped connection is never leaving.
- **Joining:** `GameSession.addPlayer(String)` (the join path) is open in the lobby and, unless the host turned off `allowLateJoin` before the start (`update-settings`), at any time after; otherwise it throws `LateJoinNotAllowedException` (REST 409). New players start at `joinScore`, which must only change in `changeScores`: it drops to any score below it, and rises (to min(lowest score, 0)) only when a player at or below it scores and nobody is left at or below it. **Every score change must go through `changeScore`/`changeScores`**, never `GameSessionPlayer.addScore` directly, or the join score goes stale. `addPlayer(GameSessionPlayer)` skips both checks and is for tests.
- **Cleanup:** every broadcast arms a per-session cleanup timer (`GameSessionTimer.scheduleCleanup`, separate from the phase timer): `IDLE_LOBBY_TIMEOUT` in `WAITING_FOR_START`, `FINISHED_SESSION_TIMEOUT` in `FINISHED_GAME`, cancelled otherwise. The callback carries the version it was armed at and is a no-op if the session changed. A departure that leaves no active players closes the session at once. `closeSession` moves it to `CLOSED` (with a `SessionCloseReason`), sends that as the last broadcast, then removes the session and its tokens; it doesn't close connections, so clients can show the closed state.
- **`GameSessionService` is the orchestration layer.** It stores sessions in a `ConcurrentHashMap`. Every mutation follows the same pattern: `synchronized (session)` → call the model method → `scheduleTimeout(session)` → `broadcast`. Keep this pattern when adding actions. The exception is an action that doesn't change the state (the Final Jeopardy wager and answer, `update-timers`, and a `leave`/`kick` that leaves the state alone): it must skip `scheduleTimeout`, because re-arming the timer would restart the phase. Concurrency control lives here, not in the model.
- **Timeouts:** `scheduleTimeout` switches on the new state and arms a single per-session timer (`GameSessionTimer`, a `ScheduledExecutorService`). Durations come from the session's own `GameSessionTimeouts` (every session starts with `GameSessionTimeouts.defaults()`; the host can change them in the lobby, validated by `SessionTimersRequest` against `MIN_MILLIS`/`MAX_MILLIS`). Timeout callbacks re-check the expected state before acting, so a stale timer is a no-op. The switch is exhaustive, so a new state won't compile until it's given a timeout or `null`. `scheduleTimeout` also records the phase on the session (`startPhaseTimer` with `System.nanoTime()`, or `clearPhaseTimer`), and `GameSessionResponse.from` turns it into `phaseDurationMs` / `phaseRemainingMs` when the response is built; tests pass their own `nowNanos` to `from(session, nowNanos)`. Every state except `WAITING_FOR_START`, `FINISHED_GAME` and `CLOSED` is timed, so an absent player can't stall a game: in `CHOOSING_CLUE` the timeout picks a clue for the chooser (`GameSession.timeoutChoosingClue`).
- Player IDs are numbered per session (1, 2, 3…, `GameSession.addPlayer(String)`), so they stay safe as JavaScript numbers but are **not unique across sessions**. They are public (every broadcast lists them); only the token proves identity, and the controller's session check is what stops a player from another session with the same id from acting. Sessions and tokens live in memory and are not persisted.
- **State version:** every broadcast goes through `GameSessionService.broadcast(session)`, which increments `GameSession.version` first; `GameSessionResponse.version` lets clients that both fetch and receive broadcasts keep the newest. Never call `broadcaster.broadcast` directly from the service.

## Testing conventions

- **Unit tests:** `GameSessionTest` exercises the state machine directly, and the service and timer tests use Mockito. The Mockito Java agent is attached in `build.gradle`.
- **Controller slice tests:** `@WebMvcTest` with `@MockitoBean`.
- **Entity IDs in tests:** entities have no ID setters, so tests set them with `ReflectionTestUtils.setField(entity, "id", ...)`.
- **REST integration tests:** `@SpringBootTest(RANDOM_PORT)`, `@AutoConfigureRestTestClient` and `@ActiveProfiles("test")`. Before/after each test they load and clean up SQL fixtures from `src/test/resources/testdata/` with `@Sql`.
- **Session tests** build `GameBoard`s from records (no entities or `ReflectionTestUtils`). `GameSessionEndToEndIntegrationTest` is the one that loads a real game from the database.
- **WebSocket integration test:** builds `GameBoard`s in memory, creates sessions and joins players directly through `GameSessionService`, and drives them with a `WebSocketStompClient` that uses `JacksonJsonMessageConverter`. Acting clients connect with `connect(tokenOf(session))` (or a second player's token); plain `connect()` is anonymous. "Wrong player" tests must use a real second player's token, since bodies have no player id.
